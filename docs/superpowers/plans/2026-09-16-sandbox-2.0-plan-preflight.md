## 1. Private DSH runtime must be a physical copy, not a shared pnpm hardlink tree

The runtime-foundation plan correctly gives every environment a distinct `runtime/` path, but a normal pnpm installation may import package files from its global/content-addressed store using hardlinks or reflinks. A different path alone is not sufficient for the Sandbox 2.0 isolation contract.

When materializing an environment runtime, pnpm MUST be configured with a copy import method so writable package files inside one environment cannot alias another environment or the shared store.

The runtime-provider implementation must install with equivalent semantics to:

```bash
pnpm --config.package-import-method=copy add --save-exact @deepseek-ai/dsh@<version>
```

If the current pnpm version requires a different spelling, use the supported spelling that guarantees ordinary copied package files rather than hardlinks/reflinks. The implementation test is authoritative.

Add this test to `test/dsh-runtime-provider.test.js`:

```js
test('same-version private runtimes do not share writable package inodes or file contents', async t => {
  const { provider, root } = realOrFixtureProvider(t)
  const a = await provider.materialize({ environmentPath: join(root, 'environments/a'), release: FIXTURE_RELEASE })
  const b = await provider.materialize({ environmentPath: join(root, 'environments/b'), release: FIXTURE_RELEASE })
  const relative = join('node_modules', '@deepseek-ai', 'dsh', 'package.json')
  const aFile = join(a.root, relative)
  const bFile = join(b.root, relative)
  const beforeB = readFileSync(bFile, 'utf8')
  writeFileSync(aFile, `${readFileSync(aFile, 'utf8')}\n`)
  assert.equal(readFileSync(bFile, 'utf8'), beforeB)
  if (process.platform !== 'win32') assert.notEqual(statSync(aFile).ino, statSync(bFile).ino)
})
```

A shared **download/cache** is still allowed. A shared writable installed runtime is not.

## 2. Official DSH release catalog must paginate and report installability

GitHub Releases remains the user-visible source of release identity. The provider must not assume the first 100 releases are the whole history, and it must not claim a release is usable merely because a GitHub tag exists.

`fetchDshReleaseCatalog()` must follow GitHub pagination until there is no next page (or until a documented explicit safety cap large enough for the repository is reached and reported as truncation). Prefer parsing the standard `Link` response header; tests use multiple fixture pages.

For every non-draft GitHub release, cross-check whether the exact `@deepseek-ai/dsh@<version>` exists in the npm registry metadata. The catalog shape becomes:

```js
{
  release: 'dsh-v0.1.6-alpha.1',
  version: '0.1.6-alpha.1',
  prerelease: true,
  publishedAt: '2026-09-15T04:57:57Z',
  available: true,
  unavailableReason: null,
}
```

If the GitHub release cannot be mapped to an installable package for the current provider, retain it in the catalog with:

```js
{
  available: false,
  unavailableReason: 'Exact @deepseek-ai/dsh package version is unavailable',
}
```

`materializePrivateRuntime()` must reject `available:false` releases before removing/replacing an existing runtime.

Add tests for:

```js
test('release catalog follows pagination and preserves stable plus prerelease releases', async () => { /* two fixture pages */ })

test('release catalog marks a GitHub release unavailable when exact DSH package version is absent', async () => { /* registry versions fixture */ })
```

The UI must disable unavailable releases and display `unavailableReason` instead of pretending the switch can work.

## 3. Runtime-foundation interface correction

In `2026-09-16-sandbox-2.0-runtime-foundation.md`, Task 1 lists `legacyRecordToEnvironment(root, legacyRecord)` as a produced interface, while Task 6 correctly treats migration as a two-phase operation requiring runtime materialization and validation.

There MUST NOT be a public conversion helper that makes a legacy record appear migrated before that two-phase process succeeds.

Use these interfaces instead:

```text
normalizeRegistryShape(data) -> registry
migrateLegacyRegistry({ root, registry, runtimeProvider, validate }) -> newRegistry
```

`legacyRecordToEnvironment` may exist only as a private pure helper used by `migrateLegacyRegistry`; it is not an externally consumable migration API and must not write the schema-v3 registry by itself.

## 4. Replace failure recovery requires an explicit automated test

The environment-transactions plan describes recovery, but the suite must prove it when failure occurs after staging/activation has begun.

Add to `test/replace.test.js`:

```js
test('failed Replace restores target managed state, target release, and target Git identity', async t => {
  const { manager, hooks } = await fixtureManager(t)
  await createAlignedSourceAndTarget(manager)
  const beforeHead = await manager.head('video')
  const beforeGit = await manager.gitDirectoryIdentity('video')
  const beforePackage = readFileSync(join(manager.getEnvironment('video').profilePath, 'package.json'), 'utf8')
  hooks.failReplaceBootAfterActivation = true
  await assert.rejects(
    manager.replace({ sourceId: 'video-test', target: { kind: 'environment', id: 'video' } }),
    /boot|validation/i,
  )
  assert.equal(await manager.head('video'), beforeHead)
  assert.equal(await manager.gitDirectoryIdentity('video'), beforeGit)
  assert.equal(readFileSync(join(manager.getEnvironment('video').profilePath, 'package.json'), 'utf8'), beforePackage)
  assert.equal(manager.getEnvironmentManifest('video').dshRelease, 'dsh-v0.1.6')
})
```

If the final implementation validates fully before activation and therefore has no legitimate post-activation validation hook, inject a filesystem activation failure after the first rename and prove deterministic restoration there instead. The requirement is that a partially progressed Replace cannot leave target state half-applied.

## 5. AI tool parameter schemas are fixed, not left to implementer interpretation

Use the following model-tool parameter contract unless the design spec is explicitly amended:

| Tool | Parameters |
| --- | --- |
| `sandbox_list` | `{}` |
| `sandbox_inspect` | `{ id: string }` |
| `sandbox_history` | `{ id: string }` |
| `sandbox_diff` | `{ id: string, ref?: string }` |
| `sandbox_releases` | `{}` |
| `sandbox_create` | `{ id: string, sourceKind: 'clean'|'stable'|'environment', sourceId?: string, release?: string }` |
| `sandbox_clone` | `{ id: string, sourceId: string }` |
| `sandbox_snapshot` | `{ id: string, message?: string }` |
| `sandbox_install_plugin` | `{ id: string, spec: string }` |
| `sandbox_start` | `{ id: string }` |
| `sandbox_stop` | `{ id: string }` |
| `sandbox_validate` | `{ id: string }` |
| `sandbox_change_dsh_release` | `{ id: string, release: string }` |
| `sandbox_reset` | `{ id: string }` |
| `sandbox_rollback` | `{ id: string, commit?: string }` |
| `sandbox_replace` | `{ sourceId: string, targetKind: 'environment'|'stable', targetId?: string }` |
| `sandbox_delete` | `{ id: string }` |
| `sandbox_recovery_list` | `{}` |
| `sandbox_recovery_restore` | `{ id: string }` |
| `sandbox_recovery_delete` | `{ id: string }` |

Tool-side argument mapping is explicit:

```js
sandbox_create -> manager action 'create' with {
  id,
  source: sourceKind === 'environment' ? { kind: 'environment', id: sourceId } : { kind: sourceKind },
  ...(release ? { dshRelease: release } : {}),
}

sandbox_replace -> manager action 'replace' with {
  sourceId,
  target: targetKind === 'stable' ? { kind: 'stable' } : { kind: 'environment', id: targetId },
}
```

No model tool named `sandbox_set_ai_control`, `sandbox_enable_yolo`, or equivalent may exist.

## 6. Add explicit YOLO STABLE-path coverage

YOLO is full Sandbox administration, including the STABLE Web-profile operations that Sandbox 2.0 exposes after version alignment.

Add to the AI-control tests:

```js
test('YOLO can replace the aligned STABLE Web profile without creating a pending action', async t => {
  const { manager } = await fixtureManager(t, { hostRelease: 'dsh-v0.1.6' })
  await manager.create({ id: 'tested', source: { kind: 'stable' } })
  manager.setAiControl('yolo', { actor: 'human' })
  const result = await manager.dispatchModelAction(
    'replace',
    { sourceId: 'tested', target: { kind: 'stable' } },
    { environmentId: 'tested' },
  )
  assert.equal(result.pending, undefined)
  assert.equal((await manager.pendingActionList()).length, 0)
})
```

This test must use the same recovery/validation path as human Replace -> STABLE.

## 7. Manager-unavailable child behavior requires explicit coverage

When the authoritative manager disappears, the child DSH may continue running but Sandbox management must fail closed.

Add tests covering both bridge client and tool synchronization:

```js
test('child Sandbox tools fail closed when the manager bridge disappears without killing the child runtime', async t => {
  const { child, bridge, toolState } = await runningChildFixture(t)
  await bridge.close()
  await toolState.pollNow()
  assert.equal(toolState.registeredSandboxToolCount(), 0)
  assert.equal(child.process.exitCode, null)
})
```

A direct bridge request after shutdown must reject with a manager-unavailable error. It must never fall back to a nested local manager or mutate a child-local registry.

## 9. Documentation sync to public `main` is a delivery requirement

The source branch release workflow creates GitHub release assets; it does not automatically synchronize source-branch README changes to public `main`.

Before using the public README as the documentation baseline in the implementation worktree, run:

```bash
git fetch origin main
git checkout origin/main -- README.md README.ru.md
```

After the Sandbox 2.0 source implementation is qualified, open a separate documentation PR to public `main` containing the final `README.md` and `README.ru.md` (and only other public-main docs/files that intentionally belong there). Do not assume publishing a `v2.0.0` tag updates public `main`.

The 2.0 delivery is not considered documentation-complete until that public-main PR is merged.

## 10. Required final test matrix additions

In addition to the four plans' test commands, final qualification must include explicit passing coverage for:

```text
- two same-version environments use independent writable runtime package files
- multi-page DSH release catalog
- unavailable GitHub release is retained but disabled/uninstallable
- failed Replace restores target completely
- rollback across DSH versions rematerializes runtime
- YOLO Replace -> STABLE executes without pending approval when versions align
- model cannot change AI mode
- child loses Sandbox tools when manager bridge disappears while child process remains alive
- Safe stale pending action cannot execute after source/target changes
- Delete recovery rebuilds private runtime from manifest
```

Run the complete suite after all additions:

```bash
npm test
```

No Sandbox 2.0 behavior may be marked complete based solely on static client source assertions; lifecycle/manager tests must cover the destructive state transitions.
