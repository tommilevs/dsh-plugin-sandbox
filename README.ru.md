# 🧪 DSH Plugin Sandbox

[English](README.md) · [Русский](README.ru.md)

**Создавай · Экспериментируй · Тестируй · Фиксируй · Сравнивай · Переноси**

**DSH Plugin Sandbox** — это менеджер отдельных окружений для **DeepSeek Harness (DSH)**, состояние которых контролируется локальным Git. Его можно использовать как временную лабораторию для проверки плагинов, но не только: sandbox может быть постоянным независимым DSH под конкретный тип задач.

У каждого sandbox есть собственный `DSH_HOME`, свой набор плагинов и настроек, а также отдельный дочерний экземпляр DSH. Состояние окружения отслеживается через Git, поэтому можно увидеть, что именно изменилось, сделать снапшот рабочего состояния и откатиться назад, если установка или обновление плагина что-то сломали.

То есть sandbox вовсе не обязан быть временным. Можно постоянно держать несколько отдельных DSH, например:

- **Coding** — плагины для разработки, репозиториев и программирования.
- **Video** — инструменты и интеграции для видеомонтажа и работы с видео.
- **Music** — отдельный DSH с плагинами для аудио и музыки.
- **Testing** — экспериментальное окружение для плагинов, которые пока не хочется ставить в основной DSH.

Главная идея проекта: **разделить разные рабочие сценарии, не смешивать наборы плагинов и сделать состояние каждого окружения обратимым благодаря локальной Git-истории.**

## Почему не просто DSH profiles?

В самом DSH уже есть profiles, и DSH Plugin Sandbox не пытается их заменить. Важное дополнение здесь в другом: каждый sandbox является отдельным DSH-окружением, состояние которого контролируется Git.

Это даёт страховку при любых изменениях плагинов и конфигурации:

- можно точно посмотреть изменения через **diff**;
- сохранить рабочее состояние в виде **snapshot**;
- посмотреть **Git history**;
- удалить незакоммиченные изменения через **Reset**;
- сделать **Rollback** после неудачной установки плагина или изменения конфигурации;
- держать несколько независимых DSH и не смешивать их наборы плагинов;
- при необходимости проверить окружение и сделать **Promote** в `STABLE`, если изменения действительно нужно перенести в основной DSH.

При этом специализированный sandbox вполне может оставаться самостоятельным постоянно. `Promote` — это один из вариантов работы, а не обязательная конечная точка каждого sandbox.

## Возможности

- **Создание независимых DSH-окружений** с собственным `DSH_HOME` и отдельным дочерним экземпляром DSH.
- Использование sandbox как **временной тестовой среды** или как **постоянного специализированного DSH**.
- Запуск с **чистого окружения** либо копирование установленных плагинов и настроек из основного профиля DSH.
- Установка плагинов из **пакета, Git-репозитория или по абсолютному локальному пути**.
- Независимый **запуск и остановка** каждого sandbox без вмешательства в основной DSH.
- **Валидация** перед переносом изменений в стабильный профиль.
- Создание именованных **Git-снапшотов** состояния sandbox.
- Просмотр **diff** и **Git history**, чтобы понимать, что именно изменилось.
- **Reset** незакоммиченных изменений и **Rollback** к предыдущему заведомо рабочему состоянию.
- **Promote** проверенного sandbox в `STABLE`; перед переносом автоматически создаётся резервная копия.
- Удаление ненужного sandbox вместе с его локальной Git-историей.

## Сценарии работы

### 1. Проверить плагин перед установкой в основной DSH

1. Откройте **🧪 Sandbox** внутри DSH.
2. Создайте новый sandbox.
3. Выберите: скопировать плагины и настройки основного DSH или начать с чистого окружения.
4. Установите или измените плагин внутри дочернего экземпляра DSH.
5. Во время тестирования создавайте снапшоты и смотрите diff.
6. Если что-то сломалось, используйте **Reset** или **Rollback**, чтобы вернуться к рабочему состоянию.
7. Когда результат готов, выполните валидацию и используйте **🚀 Promote**, чтобы перенести его в `STABLE`.
8. Перезапустите основной экземпляр DSH, чтобы применить обновлённый стабильный профиль.

### 2. Держать несколько постоянных DSH под разные задачи

Создайте отдельный sandbox для каждого типа работы и оставьте в нём только нужные плагины. Например, можно постоянно держать `Coding`, `Video` и `Music` как независимые окружения и запускать нужное в зависимости от текущей задачи.

У каждого такого DSH есть собственная Git-история. Поэтому установка или обновление плагина в `Video` не затрагивает рабочее состояние `Coding`, а после неудачного эксперимента можно откатить только конкретный sandbox, не собирая его заново с нуля.

Такие окружения вообще не обязательно переносить в `STABLE` — они могут оставаться отдельными столько, сколько нужны пользователю.

## Установка

```bash
dsh plugin --profile web add dsh-plugin-sandbox
```

## Локализация

Локализация — это удобная дополнительная возможность проекта, а не его основная идея.

Sandbox имеет встроенные **английскую** и **русскую** локализации и поддерживает языки сообщества. В репозитории уже присутствует и **немецкая** локализация сообщества.

Режим `🌐 Auto` использует язык браузера, если для него существует подходящая локализация, а иначе переключается на английский.

Каждая локализация состоит из файла строк интерфейса и файла метаданных:

```text
locales/<code>.json
locales/metadata/<code>.json
```

Интерфейс Sandbox помогает установить перевод локально и подготовить изменение для отправки в GitHub. Он также показывает прогресс перевода и подсвечивает строки, которые ещё нужно перевести после изменения английской схемы.

### Как добавить или обновить язык

Для нового языка необходимо добавить и файл перевода, и соответствующий metadata-файл. Для уже существующей локализации сообщества можно изменить только `locales/<code>.json`, если метаданные языка не менялись.

Проверить локализацию локально можно так:

```bash
node scripts/validate-locale.mjs \
  locales/en.json \
  locales/de.json \
  locales/metadata/de.json
```

Pull request'ы с локализациями сообщества проверяет **Locale Guard**. Workflow принимает один файл перевода и, при необходимости, соответствующий metadata-файл, сверяет перевод с канонической английской схемой и не выполняет код из pull request. Исходная английская локализация не участвует в автоматическом community auto-merge. Корректные PR с переводами могут автоматически получить approve и быть добавлены через squash auto-merge после успешного прохождения проверок.

## Граница безопасности

> **Это sandbox для разработки и управления состоянием, а не средство изоляции на уровне операционной системы.**

Плагины по-прежнему выполняются с правами пользователя, под которым запущен DSH. DSH Plugin Sandbox предоставляет отдельное состояние DSH, разделение процессов, Git-историю и откат, валидацию, резервное копирование и контролируемый `Promote`. Основная защита здесь — от нежелательных или сломанных изменений состояния, а не от вредоносного кода, способного выйти за границы системной изоляции.

Для действительно враждебного кода используйте полноценную изоляцию на уровне ОС, контейнера или виртуальной машины.
